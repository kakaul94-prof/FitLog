=== Strength goal planning ===

Per-exercise strength goals + a progression engine that suggests the weight/reps
for upcoming workouts toward a target. Goal = a target 1RM per lift; current
strength is derived LIVE from logged workout_sets (Epley e1RM), never stored, so
switching method never resets progress. Three switchable methods, each shown
in-app with its reasoning + source (PROGRESSION_SOURCE in src/lib/progression.ts):
  - linear — +step each session you hit the reps; deload 10% after 2 stalls (Starting Strength / StrongLifts)
  - double — add reps across a range, then weight; deload on stall (NSCA 2-for-2 rule / ACSM)
  - 5/3/1 — % of a training max in weekly waves (W1 5s / W2 3s / W3 5-3-1 / W4 deload), AMRAP last set, TM +step per cycle (Wendler)

=== Known bugs (open) ===

- [BUG 2026-07-19] Editing a logged cardio entry's DURATION doesn't re-estimate the burn for exercises that were logged at a different bodyweight than your current latest weight (reported on "Weight training (general)"; "Walking (treadmill)" updates fine because it was logged at the current weight — same code path, so it's data-specific, not activity-specific). Root cause: exercise_entries store no log-time bodyweight, so ExerciseAddPage's edit-prefill recomputes the estimate from the CURRENT latest weight (metCalories ← useLatestWeight) and, when it ≠ the stored calories, mis-reads it as a manual watch-override → setOverride(entry.calories) (src/pages/ExerciseAddPage.tsx:158), which then PINS the displayed burn (calories = override ? … : est, line 117) so the duration field no longer drives it. NOT a code regression — the override/est/prefill code is unchanged since early June, weight_training MET has been 3.5 since the first commit, and useLatestWeight (no averaging/unit change) is unchanged since 2026-06-19; the trigger is logging a NEWER weight than when that session was logged, which is why it "worked before" (verified via git blame + log). WORKAROUND (confirmed): re-log the exercise fresh — a new log uses current weight so the estimate tracks; also clearing the auto-filled Override box on the edit screen unfreezes it. FIX LATER: stop inferring the override from a calorie mismatch — store an explicit "manual override" flag on the entry, or snapshot the log-time bodyweight so the recompute matches (relates to line 7 "preserves a manual watch-override" + line 4 "new logs use latest weight at log time"). Watching for now; not fixing yet.
